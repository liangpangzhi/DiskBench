> 分析对象：`diskbench-x86_64-0.1.36.fpk`（8.2 MB，飞牛 fnOS 第三方应用安装包）

## 一、结论摘要

`diskbench-x86_64-0.1.36.fpk` 是一个 **gzip 压缩的 tar 包**，内部是飞牛 fnOS 的标准应用安装结构。它是开源项目 **Disk Bench**（作者：情深深雨蒙蒙 / yueqihe，MIT 协议）的 x86_64 发行包，一款用于 fnOS 的硬盘健康检测与性能测速工具。

- **后端**：Go 1.26 编译的静态二进制（10 MB，musl libc，CGO 关闭），plus fio / smartctl 两个捆绑工具，通过 **Unix Domain Socket** 提供 HTTP API，仅管理员可用，root 运行。
- **前端**：React 19 + Vite 7 + lucide-react，纯静态资源，打包进二进制同级 `public/` 目录。
- **能力**：SMART 信息、快速/全盘坏道扫描、异常扇区定位、断点续扫、慢扇区修复、NVMe 固件自检、CrystalDiskMark 风格读写测速、历史与 HTML 报告导出。
- **二次开发可行性**：★★★★★。源码完整（73 个 Go 文件约 1.96 万行 + 前端 5.4k 行），构建脚本齐全，本地可交叉编译并重新打包 FPK。

| 字段 | 值 | 说明 |

### 生命周期脚本要点（`cmd/main`）

- 启动：校验 PID 与 `/proc/$pid/exe` 防止僵尸/复用，设置环境变量后后台运行后端。
  ```
  LOCAL_DEV=0 MOCK_DEV=0 DATA_DIR=$TRIM_PKGVAR \
  GATEWAY_PREFIX=/app/diskbench SOCKET_PATH=$TRIM_APPDEST/app.sock ./diskbench
  ```
- 停止：先 SIGTERM，轮询最多 10 秒等待在途磁盘 I/O / 固件自检中止完成，超时则报错拒绝卸载。
- 卸载：向导选择保留/删除历史；`uninstall_callback` 仅允许删除 `$TRIM_PKGVAR/../@appdata/diskbench/jobs` 及旧版备份，带完整路径校验防止误删。修复备份目录 `repair-backups/` 永不自动删除。

## 三、系统架构

```
┌─────────────────────────────────────────────────────────┐
│  fnOS 宿主 (反向代理 /app/diskbench/* → unix socket)      │
│  注入 X-Trim-Isadmin / X-Trim-Username 请求头              │
└───────────────────────┬─────────────────────────────────┘
                        │ HTTP over Unix Domain Socket (app.sock)
┌───────────────────────▼─────────────────────────────────┐
│  Go 后端 (root)                                          │
│  ├─ apiServer     路由 / 鉴权 / CSP / JSON               │
│  ├─ JobManager    任务引擎（创建/取消/持久化/并发仲裁）    │
│  │   ├─ 扫描引擎   blockScanHandle / nvmeScanHandle       │
│  │   ├─ 测速引擎   runFioBenchmark / streamFioSample      │
│  │   ├─ 修复引擎   scanRepair / recordedRepair            │
│  │   └─ 报告       prepareScanHTMLReport / scanReport     │
│  ├─ deviceService lsblk/findmnt → Disk / StorageSpace     │
│  └─ smartReport   smartctl JSON 解析                      │
│  外部依赖：fio（测速）、smartctl（SMART）、dd、lsblk、      │
│            findmnt、fstrim（TRIM）                         │
└─────────────────────────────────────────────────────────┘
                        │ 静态文件
┌───────────────────────▼─────────────────────────────────┐
│  React 19 前端 (SPA)  main.jsx + job-model.js            │
│  页面：坏道扫描 / 磁盘测速 / 历史记录 / SMART 查看         │
│  特性：浅/深色主题、块图、实时进度、报告导出              │
└─────────────────────────────────────────────────────────┘
```

**通信约定**：前端以 `import.meta.env.BASE_URL + '/api'` 作为 API 前缀（即 `/app/diskbench/api`）；写操作带 `X-Requested-With: DiskBench` 头做 CSRF 防护；后端强制 `X-Trim-Isadmin: true`（本地开发模式跳过）；CSP 严格限制 `default-src 'self'`。

## 四、后端分析（Go）

### 4.1 入口与运行模式（`backend/main.go`）

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| GATEWAY_PREFIX | /app/diskbench | API/静态资源路由前缀 |
| SOCKET_PATH | 空 | 非空时监听 Unix Socket，否则 TCP |
| PORT | 5050 | TCP 监听端口 |
| LISTEN_HOST | 127.0.0.1 | TCP 监听地址 |
| LOCAL_DEV | 0 | 1=本地开发（放宽鉴权/CSP/frame） |
| MOCK_DEV | 0 | 1=模拟设备（需同时 LOCAL_DEV=1） |
| DATA_DIR | ./data | 任务历史与日志目录 |
| FRONTEND_DIST | ./public | 静态资源目录 |

信号 SIGTERM/SIGINT → 优雅关闭 JobManager → Shutdown HTTP → 删除 socket。

### 4.2 HTTP API 契约（`backend/server.go`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 能力探测（scan/dd/fio/fstrim/smart/mock）、用户信息、测试计划 |
| GET | `/api/disks` | 磁盘清单 + 存储空间清单（可含 storageWarning） |
| GET | `/api/disks/smart?device=<path>` | 指定磁盘原始 SMART 报告 |
| GET | `/api/jobs[?summary=1&active=1&include=id]` | 任务列表（支持摘要/仅活跃） |
| POST | `/api/jobs` | 创建任务（需 X-Requested-With） |
| GET | `/api/jobs/{uuid}` | 任务详情 |
| DELETE | `/api/jobs/{uuid}` | 删除历史（需 X-Requested-With） |
| POST | `/api/jobs/{uuid}/cancel` | 取消任务（需 X-Requested-With） |
| GET | `/api/jobs/{uuid}/scan-progress?after=N` | 扫描块图增量进度 |
| GET | `/api/jobs/{uuid}/scan-issues?offset=&limit=&view=ranges` | 异常明细分页（1≤limit≤200） |
| GET | `/api/jobs/{uuid}/scan-report?format=html\|json` | 导出扫描报告（附件下载） |

任务 ID 正则：`(?i)^[0-9a-f-]+$`。错误响应统一 `{"error": "...", "code": "..."}`，如 `ADMIN_REQUIRED`(403)、`ACTIVE_JOB_CONFLICT`(409)、`DISK_IDENTITY_CHANGED`(409)、`JOB_NOT_FOUND`(404)、`REQUEST_SOURCE_INVALID`(403)、`JOB_TYPE_RETIRED`(410)。

### 4.3 创建任务参数（POST /api/jobs，`validateCreateJobBody`）

必填：`type`（`scan` | `speed`，`write` 已停用）、`device`（磁盘路径）。
扫描参数：`scanMode`(quick/full)、`scanExactSectors`、`scanSelfTest`、`scanRepair`、`scanRepairAfterMs`(1–60000)、`scanRepairAcknowledged`、`resumeFrom`、`scanRepairFrom`。
测速参数：`sampleMiB`(16MiB–64GiB)、`speedRuns`(1–9)、`speedPreset`、`speedPosition`(all/start/middle/end)、`speedOperation`(read/write/mixed)、`speedPattern`(sequential/random)、`speedBlockSize`(4096/65536/1MiB/4MiB)、`speedQueueDepth`(1/8/16/32/64/128)、`speedThreads`(1/2/4/8)、`speedIOEngine`(io_uring/psync)、`speedProfileRow`、`speedTarget`(filesystem/raw)、`speedDirectIO`、`speedTrim`、`speedProfile`、`rawWriteAcknowledged`。
一致性校验：`expectedDisk`（path/serial/model/size）、`expectedStorageSpace`（path/source/fileSystem/layout/members/readOnly/size）防止目标被调包。

### 4.4 核心数据模型

- **Disk**：id/name/path/size/model/serial/transport/扇区大小/是否旋转/只读/挂载点/文件系统/是否系统盘 + SMART 子集（温度、通电时间、重写写量、寿命百分比、重映射扇区 ATA5、待映射 197、不可纠正 198/187、NVMe media errors、critical_warning）。
- **StorageSpace**：path/source/fileSystem/layout/members/size/freeBytes/readOnly/isSystem。
- **Job**：id/type/device/disk 快照/status/historyOrder/progress/phase/时间戳/message/result/log/options。
- **ScanProgressSnapshot / ScanResult**：4096 单元的块图（每单元响应等级）、异常范围、慢块统计、修复统计。
- **SpeedResult / SpeedSample / SpeedLiveStatus**：每轮每项的 MB/s、IOPS、延迟、实时进度。
- **SmartReport**：原始文本 + 解析后的属性表。

### 4.5 关键业务逻辑

- **并发仲裁**（`job_conflicts.go`）：不同硬盘可并行扫描/测速；同一硬盘同时只跑一个任务；全局一次只跑一个测速；存储空间测速按成员硬盘判冲突；停止中的任务会等待其释放硬盘。
- **扫描引擎**：全盘顺序读（`blockScanHandle`）或 NVMe 固件自检 + 底层读（`nvmeScanHandle`）；分层 reader 链做慢读复测、异常定位、预算控制、负载监测；延迟门槛 SSD/NVMe 500ms、HDD 800ms；排除可观测系统负载后才判为坏块。
- **断点续扫**：任务状态持久化到 `$DATA_DIR/jobs`，重启后 `loadJobs` 恢复；点击开始扫描时对同一磁盘提示"继续/重新开始"。
- **慢扇区修复**：仅处理能完整读出且复读一致的准确范围 → 备份原始数据 → 原址写回 → 读回校验 → 同范围复测；写回校验通过 ≠ 慢速改善。
- **测速引擎**：fio 流式 JSON 采样（`decodeFioStream`/`parseFioSample`），CDM 四组配置，每项预跑一轮 + 每轮计时 5 秒 + 间隔 5 秒，取最快一轮平均值；文件测速用临时文件并保留 ≥1GiB 且 ≥10% 容量；底层写/混合需输入 `ERASE` 确认，具有破坏性。
- **报告**：可在后端直接生成离线 HTML（`scan_report.html` + `scan_report.css` 模板，`scan_report_html.go`）或 JSON。

## 六、构建与打包流程

```bash
npm ci                       # 安装依赖（含 workspace frontend）
npm test                     # node --test backend/test + Go 测试
npm run demo                 # 本地模拟数据演示 → http://127.0.0.1:5050/app/diskbench/
npm run serve                # 本地真实后端预览

# 构建 FPK（建议 Linux / WSL，需 Go 1.22+ 与 fnpack）
node scripts/download-fnpack.js
npm run fpk:amd64 -- --nosign    # 生成 x86_64 未签名包
npm run fpk:arm64 -- --nosign    # 生成 arm64 未签名包
```

构建链（`package.json` scripts）：`build:icons`（APNG 图标）→ `build:frontend`（vite build）→ `build:go`（`go build -trimpath -ldflags="-s -w"` 交叉编译 Linux amd64/arm64）→ `stage`（组装 package/diskbench/app/server）→ `fnpack.js build`（fnOS 打包，支持开发者证书签名）。

- `scripts/build-go.js`：CGO_ENABLED=0，输出 `backend/diskbench`。
- `scripts/stage.js`：拷贝后端二进制 + 前端 dist + 对应架构 runtime-deps + 许可证到打包目录。
- `scripts/set-platform.js`：写入 manifest 的 platform/version/changelog。
- 签名：设置 `FNPACK_KEY`/`FNPACK_CERT` 或预先导入 fnpack 证书；`--nosign` 用于本地调试。

## 七、二次开发指南

### 7.1 推荐工作流

1. 在 Linux/WSL 中准备本仓库（`DiskBench/`）。Windows 本机可先跑 `npm run demo`（纯前端 + Go mock）验证 UI。
2. 修改代码 → `npm test` → `npm run fpk:amd64 -- --nosign` → 在 fnOS 应用中心"手动安装"测试。
3. 需要正式分发时导入飞牛开发者证书签名打包。

### 7.2 常见改造点

| 目标 | 修改位置 |
|---|---|
| 改应用名/版本/描述/作者 | `package/diskbench/manifest` + `scripts/set-platform.js` |
| 改 UI 文案、主题、布局、图标 | `frontend/src/main.jsx`、`styles.css`、`assets/icon-source.svg` |
| 增加/调整测速预设与参数 | 后端 `job_manager.go`（`createSpeedPlan`/speed 常量）+ 前端 `job-model.js` + `server.go` 校验 |
| 新增 API 接口 | `backend/server.go`（`allowedApiMethods` + `handleApi`）+ 前端 `api()` 调用 |
| 修改扫描阈值/判定规则 | `scan_verdict.go`、`scan_latency.go`、`scan_recheck.go`、`scan_read_linux.go` |
| 修改报告模板 | `scan_report.html` / `scan_report.css` / `scan_report_html.go` |
| 调整卸载/历史策略 | `cmd/*`、`wizard/uninstall` |
| 更换 API 前缀 | `main.go` GATEWAY_PREFIX + `vite.config.js` base + 前端 API 常量 |

### 7.3 开发调试技巧

- `LOCAL_DEV=1 MOCK_DEV=1`：无需真实磁盘与 root 即可用 3 块模拟盘（NVMe 990 PRO / WD 紫盘 / 870 EVO）跑通全流程。
- 后端契约测试用 JS 启动真实二进制并断言 JSON 响应，改造 API 后务必同步更新 `backend/test/*.test.js`。
- 前端锁定 React 19 / Vite 7，改动依赖注意 `package-lock.json`。

### 7.4 注意事项与风险

- 后端以 **root** 运行，涉及裸设备读写，任何改动都需谨慎验证路径校验与一致性校验，避免误写系统盘。
- 底层写/混合测速与慢扇区修复具有**破坏性**，改造时不要移除 `ERASE`/`REPAIR` 二次确认与设备身份校验。
- fnOS 升级会保留 `$TRIM_PKGVAR`（jobs 历史），改造数据结构时需考虑旧记录兼容。
- 分发 FPK 需同时提供第三方源码附件（`runtime-deps/sources.json`），并遵守各组件（fio GPL、smartmontools GPL、musl 等）许可证；Disk Bench 本体为 MIT。
